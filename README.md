### 混合负载下交易并发框架代码功能

#### 面向混合负载（长交易+短交易）高性能区块链执行引擎，需实现4项核心机制：
   1. 批次生成（即确定水位线，Determinate watermark）
   2. 分级试探执行（Prioritized speculative execution）
   3. 最大提交验证（Commit-maximum validation
   4. 交易重执行（Tx re-execute）
   5. 水位线间并发（Inter-watermark concurrency）

#### 一.交易批次生成模块
**输入**：区块中的原始交易序列（按共识顺序）
**输出**：多个批次交易Batch 1, Batch 2, Batch 3... Batch n
**总体目标**：负责根据输入的区块交易序列，生成满足如下规则的执行批次

步骤如下：
1.批次根据水位线进行划分，水位线位置以长交易为基准进行定义
2.第i个水位线的位置是第CPU核数×α×i笔长交易所属的交易ID
3.一个批次包含从上一水位线（不含）到当前水位线（含）之间的所有交易

2.分级试探执行

输入：由交易批次生成模块产生的不同批次交易
输出：表示交易之间冲突关系的有向无环图
总体目标：负责根据输入的区块批次，生成交易冲突有向无环图

步骤如下：
1.对批次内交易并发执行，线程优先去处理长交易，再处理短交易，执行过程中收集读写
2.线程根据交易ID以及相应的读写集，构建有向无环图，线程构造完再合并DAG

其中，合并DAG的算法如下：
执行过程中，每个线程维护状态读写表（read-write table），每个状态对应一个表，表包含2项，分别是：
①address：状态的地址
②readers and writers：读/写该状态的交易情况（txID, 操作类型）（按照交易号递增组织）

例：
线程1：
address: 0x82963.....
readers and writers: [(1, r),(4, w),(5, r),(9, w),(10, w)]

线程2：
address: 0x82963.....
readers and writers: [(2, r),(3, w),(6, r),(7, w),(8, w)]

基于不同线程之间对相同key构建的状态读写表，来对DAG进行合并，过程类似于合并两个有序的单链表：

设置两个指针分别指向两个线程readers & writers队列队首，按照id递增逐个处理。

假设当前分析的交易为txi，上一笔处理的交易为txj，原队列中txj的下一笔交易为txk

如果txj操作为write，DAG中添加由txj指向txi的边，删除原本txj指向txk的边，增加txi到txk的边

3.最大提交验证

输入：交易冲突有向无环图
输出：可提交的交易集合，被中止的交易集合
总体目标：基于交易冲突关系构建的有向无环图，基于动态规划求解一个在满足无冲突约束条件下、使提交交易总计算量最大的交易子集。

步骤如下：
1.不同线程分别对冲突图的不同子图分区进行处理，独立筛选出可提交的交易
2.每个线程采取以下规则对子图进行处理：

dp[i] = max(
dp[i+1],                       // 不提交i
cost[i] + dp[next_non_conflict(i)] ) // 提交i
dp[i]表示从交易i能够提交的最大工作量，next_non_conflict表示后面与i不冲突的交易
如果交易为计算型，cost[i]取lamda（这个值是否可以根据执行进行定）
（可以加，跑以太坊交易，记录不同指令时间，结果作为参数）
如果是嵌套合约，要特殊处理/注意

4.重执行

输入：验证阶段中止的交易
输出：可以提交以及被中止的交易集合
总体目标：依据交易在前次执行阶段产生的读写集，将读写集存在冲突的交易分配给同一个线程执行，以此降低因读写集冲突导致。重执行验证不通过交易放入下一批。

5.水位线间并发

#### 在分级试探执行阶段，采用MVCC进行并发执行，如果当前批次交易已经执行完，空余线程采取MVCC开始执行下一个Batch的交易，提高CPU利用率，但不能所有的线程都去执行下一个Batch的交易，必须保留部分线程用于当前批次的交易执行完成之后的验证，理论上，假设有n个线程，那么需要保留n/2的线程来做验证；假设此时有4个线程，现在，线程1执行完之后，发现当前Batch已经没有交易可以执行了；但是还有3个线程在执行当前Batch的交易，所以线程1可以执行下一个Batch的交易；线程2同理；但是对于线程3来说，它也没有当前Batch的交易可执行了，此外，由于已经有n/2个线程去执行下一Batch的交易了，那么它可以开始进行验证了。
如果检查到下一批次的某个交易与上一个批次发生冲突，提前中止该交易（early abort）。
当前一个批次交易的验证阶段结束后，当前批次被提前中止的交易可以开始继续执行。
