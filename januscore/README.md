### 混合负载下交易并发框架代码功能

#### 面向混合负载（长交易+短交易）高性能区块链执行引擎，需实现4项核心机制：
   1. 批次生成（即确定水位线，Determinate watermark）
   2. 分级试探执行（Prioritized speculative execution）
   3. 最大提交验证（Commit-maximum validation
   4. 交易重执行（Tx re-execute）
   5. 水位线间并发（Inter-watermark concurrency）

#### 一、交易批次生成模块
**输入**：区块中的原始交易序列（按共识顺序）
**输出**：多个批次交易Batch 1, Batch 2, Batch 3... Batch n；每个批次分为长交易和短交易两部分
**总体目标**：负责根据输入的区块交易序列，生成满足如下规则的执行批次

#### 步骤如下：
1. 批次根据水位线进行划分，水位线位置以长交易为基准进行定义
2. 第i个水位线的位置是第CPU核数×α×i笔长交易所属的交易ID
3. 一个批次包含从上一水位线（不含）到当前水位线（含）之间的所有交易
4. 考虑到长短交易出现概率不均衡的情况，设定β参数，如果某一批次内长交易数量未达到CPU核数×α时，且该批次内交易总数达到β×CPU核数时，则视该批次为完整批次，直接结束该批次的交易添加；否则，继续添加长交易，直到该批次内长交易数量达到CPU核数×α或该批次内交易总数达到β×CPU核数为止。其中，α=1.5, β=3.5 为经验值，可根据实际情况进行调整。
5. 具体算法如下：
   1. 初始化第一个批次，设置当前批次交易总数为0，当前批次长交易数量为0
   2. 遍历区块中的交易序列，对于每笔交易，判断其为长交易还是短交易
   3. 如果当前交易为长交易，则将当前批次长交易数量加1
   4. 将当前交易添加到当前批次中，当前批次交易总数加1
   5. 判断当前批次是否满足结束条件：
      - 如果当前批次长交易数量达到CPU核数×α，结束当前批次，开始下一个批次
      - 否则，如果当前批次交易总数达到β×CPU核数，结束当前批次，开始下一个批次
   6. 重复步骤2-5，直到遍历完所有交易
   7. 输出所有生成的批次



#### 二、分级试探执行
**输入**：每次输入一个批次的交易集合
**输出**：为该批次的交易生成读写集
**总体目标**：通过并发+MVCC的方式执行批次内的交易，生成每笔交易的读写集，同时在某一批次的执行末端，根据(五、水位线间并发)开始流水并行执行下一个批次的交易

#### 步骤如下：
1. 利用MVCC对批次内的交易并发执行，线程优先去处理长交易，再处理短交易，执行过程中收集读写集
2. 如果当前批次交易已经执行完，空余线程则继续并发执行下一批交易，提高CPU利用率
3. 但不能所有的线程都去执行下一批交易，必须保留部分线程用于当前批次的交易执行完成之后的验证，即(三、最大提交验证)
4. 理论上，假设有n个线程，那么需要保留n/2的线程来做验证；假设此时有4个线程，现在，线程1执行完之后，发现当前批次已经没有交易可以执行了；但是还有3个线程在执行当前批次的交易，所以线程1可以执行下一个批次的交易；线程2同理；但是对于线程3来说，它也没有当前批次的交易可执行了，此外，由于已经有n/2个线程去执行下一批次的交易了，那么它可以开始进行验证了。
5. 具体算法如下：
   1. 初始化线程池，设定线程数量为CPU核数n
   2. 线程优先从当前批次的长交易队列中获取交易进行执行
   3. 执行完长交易后，线程从当前批次的短交易队列中获取交易进行执行
   4. 执行过程中，收集每笔交易的读写集
   5. 当当前批次的交易执行完毕后，检查是否有空余线程
   6. 如果有空余线程，允许这些线程从下一个批次的交易队列中获取交易进行执行
   7. 但必须保留n/2个线程用于当前批次的验证工作
   8. 重复步骤2-7，直到所有批次的交易执行完毕
   9. 输出每笔交易的读写集

#### 三、最大提交验证

**输入**：当前批次所有交易的读写集
**输出**：可提交的交易集合，被中止的交易集合
**总体目标**：基于交易读写集构建的有向无环图，基于动态规划求解一个在满足无冲突约束条件下、使提交交易总计算量最大的交易子集。

#### 步骤如下：
1. 根据(二、分级试探执行)的步骤可知，当前批次的交易已经并发执行完毕，并且每笔交易的读写集已经收集完毕
2. 利用多线程来构建集构建交易冲突图DAG，根据(二、分级试探执行)的步骤，当线程3完成当前批次的执行时，那么它就可以开始构建冲突图DAG，它可以为本线程执行的交易和线程1执行的交易构建冲突图DAG；当线程4完成时，线程4也可以为本线程执行的交易和线程2执行的交易构建冲突图DAG(两个交易之间可能有多条边，因为它们每有一个状态冲突就会有一条边)；最终，线程3和线程4分别构建出两个子DAG
3. 采用多线程对冲突图DAG进行两两合并与处理，直至剩下一个完整的冲突图DAG
4. 完整的DAG里可能又有多个DAG(如 tx1->tx2, tx3->tx4是合并后该批次的完整DAG，但tx1->tx2和tx3->tx4分别是两个独立的DAG)，此时需要得出每个独立DAG，方便后面并发地求解每个DAG的最大提交交易子集
5. 并发地通过动态规划求解每个DAG的最大提交交易子集
6. 具体算法如下：
   1. 构建冲突图DAG
   2. 合并冲突图DAG
   3. 求解最大提交交易子集

#### 3.1 合并冲突图DAG
其中，合并DAG的算法如下：
1. 执行过程中，每个线程维护独立的状态读写表`read-write table`，每个状态对应一个表，表包含2项，分别是：
    > `address`：状态的地址
    >
    > `readers and writers`：读/写该状态的交易情况（`txID`, 操作类型）（按照交易号递增组织）
   1. 例： 
      - 线程1：
        > address: 0x82963.....
        > 
        > readers and writers: [(1, r),(4, w),(5, r),(9, w),(10, w)]
      - 线程2：
        > address: 0x82963.....
        >
        > readers and writers: [(2, r),(3, w),(6, r),(7, w),(8, w)]

2. 基于不同线程之间对相同key构建的状态读写表，来对DAG进行合并，过程类似于合并两个有序的单链表： 
3. 设置两个指针分别指向两个线程readers & writers队列队首，按照id递增逐个处理。 
4. 假设当前分析的交易为txi，上一笔处理的交易为txj，原队列中txj的下一笔交易为txk 
5. 如果txj操作为write，DAG中添加由txj指向txi的边，删除原本txj指向txk的边，增加txi到txk的边(**这个需要帮忙确认是否正确**)

#### 3.2 动态规划求解每个DAG的最大提交交易子集
不同线程分别对冲突图的不同子图分区进行处理，独立筛选出可提交的交易
每个线程采取以下规则对子图进行处理：
图示如下：
```tx0 → tx1 → tx2 → tx3 → ... → txn
dp[i] = max(dp[i+1],                            // 不提交i
            cost[i] + dp[next_non_conflict(i)]  // 提交i
            ) 
// dp[i]表示从交易i能够提交的最大工作量，next_non_conflict表示后面与i不冲突的交易
```
交易的`cost`为交易执行过程中生成的`ExecutionCost`字段

#### 四、交易重执行
**输入**：验证阶段中止的交易
**输出**：可以提交以及被中止的交易集合
**总体目标**：依据交易在前次执行阶段产生的读写集，将读写集存在冲突的交易分配给同一个线程执行，以此降低因读写集冲突导致的重执行次数。重执行验证不通过交易放入下一批。
#### 步骤如下：
1. 根据(三、最大提交验证)的步骤可知，当前批次的交易已经验证完毕，并且每笔交易的读写集已经收集完毕
2. 利用多线程来对被中止的交易进行重执行

#### 五、水位线间并发

#### 水位线间并发需要解决两个核心问题：以进行线程调度，避免资源浪费(因此上面所有的处理应该编成任务来用线程池来调度)
1. 如何在当前批次的交易执行阶段，提前开始下一个批次的交易执行
2. 验证阶段如何执行下一批次的交易，下一批次的交易和当前批次的交易冲突怎么处理
3. 主要思路(需完善)：
   1. 在分级试探执行阶段，采用MVCC进行并发执行，如果当前批次交易已经执行完，空余线程采取MVCC开始执行下一个Batch的交易，提高CPU利用率
   2. 但不能所有的线程都去执行下一个Batch的交易，必须保留部分线程用于当前批次的交易执行完成之后的验证，理论上，假设有n个线程，那么需要保留n/2的线程来做验证；
   3. 假设此时有4个线程，现在，线程1执行完之后，发现当前Batch已经没有交易可以执行了；但是还有3个线程在执行当前Batch的交易，所以线程1可以执行下一个Batch的交易；线程2同理；但是对于线程3来说，它也没有当前Batch的交易可执行了，此外，由于已经有n/2个线程去执行下一Batch的交易了，那么它可以开始进行验证了。
   4. 如果检查到下一批次的某个交易与当前批次发生冲突，提前中止该交易（early abort）
   5. 当前一个批次交易的验证阶段结束后，当前批次被提前中止的交易可以开始继续执行。
